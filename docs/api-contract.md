# AI Customer Support Agent API Contract

## Overview

This document defines the HTTP contract for the AI Customer Support Agent API.

The API currently exposes two endpoints:

- `GET /health`
- `POST /chat`

All responses use JSON.

The API uses API Gateway HTTP API with Lambda proxy integration and payload format version `2.0`.

Authentication is not included in the current version.

---

## General response headers

Successful and controlled error responses must include:

```http
Content-Type: application/json
```

---

## Request ID

Responses produced by the application include a `request_id`.

The request ID is used to correlate:

- the HTTP response;
- the API Gateway request;
- the Lambda invocation;
- CloudWatch logs.

Example:

```json
{
  "request_id": "abc123"
}
```

Clients should treat the request ID as an opaque string.

---

# GET /health

Returns the current health status of the application.

This endpoint only confirms that API Gateway and the Lambda application are reachable.

It does not verify external dependencies such as Bedrock, SQS, databases, or third-party services.

## Request

```http
GET /health
```

The request does not require a body or query parameters.

## Successful response

### Status

```http
200 OK
```

### Body

```json
{
  "status": "ok",
  "service": "ai-customer-support-agent",
  "environment": "dev"
}
```

### Fields

| Field | Type | Description |
|---|---|---|
| `status` | string | Current application status |
| `service` | string | Service name |
| `environment` | string | Current deployment environment |

---

# POST /chat

Receives a user message and returns the response generated by the support application.

The current implementation returns a static response. Bedrock integration will be added in a later phase.

## Request

```http
POST /chat
Content-Type: application/json
```

### Body

```json
{
  "message": "Where is my order?"
}
```

### Fields

| Field | Type | Required | Description |
|---|---|---|---|
| `message` | string | Yes | Message submitted by the user |

## Validation rules

The request body must:

1. contain valid JSON;
2. be a JSON object;
3. contain the `message` field;
4. contain `message` as a string;
5. contain at least one non-whitespace character;
6. contain no more than 4,000 characters;
7. contain no unknown fields.

Leading and trailing whitespace may be removed before processing.

## Successful response

### Status

```http
200 OK
```

### Body

```json
{
  "data": {
    "message": "Where is my order?",
    "response": "The support agent is not connected to AI yet."
  },
  "request_id": "abc123"
}
```

### Fields

| Field | Type | Description |
|---|---|---|
| `data.message` | string | Normalized user message |
| `data.response` | string | Response produced by the application |
| `request_id` | string | Request correlation identifier |

# Error format

Controlled application errors use the following structure:

```json
{
  "error": {
    "code": "INVALID_REQUEST",
    "message": "The field 'message' is required."
  },
  "request_id": "abc123"
}
```

## Error fields

| Field | Type | Description |
|---|---|---|
| `error.code` | string | Stable machine-readable error code |
| `error.message` | string | Human-readable error description |
| `request_id` | string | Request correlation identifier |

Clients should use `error.code` for programmatic decisions.

Clients should not depend on the exact text of `error.message`.

---

## Method not allowed

Example:

```http

```

### Status

```http
405 Method Not Allowed
```

### Body

```json
{
  "error": {
    "code": "METHOD_NOT_ALLOWED",
    "message": "The HTTP method is not allowed for this route."
  },
  "request_id": "abc123"

```

# Internal errors

Unexpected application errors must not expose internal implementation details.

The response must not include:

- stack traces;
- exception names;
- file paths;
- environment variables;
- credentials;
- infrastructure details.

## Status

```http
500 Internal Server Error
```

## Body

```json
{
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "An unexpected error occurred."
  },
  "request_id": "abc123"
}
```

The complete error should be written to CloudWatch Logs with the same request ID.

---

# Status code summary

| Status | Meaning |
|---|---|
| `200` | Request processed successfully |
| `400` | Invalid request body or input |
| `404` | Route does not exist |
| `405` | HTTP method is not allowed for the route |
| `500` | Unexpected internal application error |

---

# Current architectural decisions

- API Gateway HTTP API is used.
- Lambda proxy integration is used.
- Payload format version `2.0` is used.
- Requests and responses use JSON.
- The maximum message length is 4,000 characters.
- Unknown request fields are rejected.
- Controlled errors use a consistent error envelope.
- Responses include a request ID.
- A `$default` route will be used for controlled routing errors.
- Authentication is not included yet.
- URL versioning such as `/v1` is not included yet.
